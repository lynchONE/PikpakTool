# 设计：全盘年份整理、同名去重与部分执行

## 范围与默认规则
- 扫描从个人网盘根目录开始，覆盖所有可读取的子目录和全部分页，排除回收站。
- 阈值严格为 100,000,000 字节；大于阈值按原始 `created_time` 的 `Asia/Shanghai` 年份归档。
- 根目录同年份文件夹按 ID 选择稳定的一个作为归档目标，其他同名年份目录作为源目录整理。根目录普通文件占用年份名称且没有可用目录时，仅跳过该年份。
- 同年份同名的大文件组成重复组，优先保留已在所选年份目录内的文件，其次大小更大、添加时间更早、ID 字典序更小。其他项进入重复删除清单。
- 同名规则来自用户明确要求，不宣称这些文件内容一致。不同年份不合并；不自动改名。

## 组件与凭据
- `api.mjs` 只访问 PikPak 文件 API，令牌存于私有内存字段，列表保留原始大小和时间，不排除未完成上传。
- `core.mjs` 负责扫描、规划、逐项核验和执行，接口适配与业务规则分离。
- `task.html` / `task.mjs` 提供连接、预览、日志三个视图。`launcher.html` 提供不依赖后台脚本的扩展入口。
- `local-api.mjs` 与 `scripts/local-server.mjs` 提供本地运行方式，复用相同界面和核心逻辑。固定 RPC 操作，不提供通用代理。
- 本地服务器校验 Host、Origin、HttpOnly/SameSite=Strict Cookie 和自定义请求头。只监听 `127.0.0.1`。每会话最多 24 个在途请求、4 个不同对象的并发写入；同一文件的移动/删除及同名建目录互斥，连接更换与全部操作互斥。客户端扫描与执行各最多使用 4 路。
- 令牌不进入文件、日志或导出。断开、停止服务或闲置 15 分钟后销毁本地凭据。连接标识变化使旧计划失效。

## 扫描与性能
1. 先完整读取根目录，以可靠识别归档目标。
2. 最多 4 个工作队列并发读取子目录，每个目录顺序读取全部分页。
3. 统一请求预留时间槽，默认至少间隔 100ms，读请求遇限流遵循有限退避；写请求不自动重试。
4. 普通子目录读取失败记录 `scanErrors` 并保护该子树，其他目录继续扫描。根目录失败、结构循环、全局连接失效或总上限触发时终止。
5. 全盘扫描生成包含所有成功读取文件的快照及操作清单。执行前不再进行第二次全盘扫描。
6. 执行期间目标列表只读取一次并随本任务的移动更新，减少大年份目录的重复分页；删除空目录时永远不使用缓存。

## 部分执行与删除依赖
- 元数据未知、时间无效、未完成上传和无法归档的同名组标记跳过；不以这些异常禁用整个执行按钮。
- 逐项检查 ID、父目录、名称、大小、原始添加时间和状态。状态变化只跳过该对象。
- 保留文件先原位核验或移动并核验，成功后记入本轮保留结果。
- 删除重复项前必须再次读取保留文件，确认其仍处于正确年份目录且大小、名称等与计划一致。保留项失败、变化或被跳过时，该组重复项全部保护。
- 小文件删除独立逐项复核，仅删除清单中且仍不超过阈值的对象。
- 目录按深度倒序、实时完整列举，仅删除空目录。根目录、所选年份目录、扫描失败目录和仍有内容的目录保护。
- 单项操作错误记录后继续其余项；登录失效、网络不可用、日志写入失败、连接更换或用户停止则终止任务。
- 所有写操作发送前记录意图，之后查询真实结果。超时只核验，不自动重放写请求。

## 并发变化限制
扫描后新增文件不加入删除清单。API 未提供本工具已确认可用的原子空目录删除条件，检查与删除间仍有并发窗口；目标列表也会在执行中缓存。整理期间应暂停其他客户端的上传和目录操作，不承诺跨客户端原子事务。

## 1.0.4 并发执行与进度
- 保留文件归档、文件删除、空目录清理分阶段执行，各阶段最多 4 个工作项并行。归档阶段全部结束后才开始重复删除；目录清理按深度分层，同层可并发，整层完成后才检查上一层。
- 并发任务共享目标目录列表加载中的 Promise，名称检查使用 Set；同时发生的相同目标/保留文件读取合并，但不长期缓存删除前保留文件的核验结果。
- 普通单项错误继续；停止、登录失效或日志写入失败时，停止启动新工作项，并等待已启动工作项核验结束再返回。写请求仍不自动重放。
- 操作意图与结果仍逐项持久化，界面日志绘制合并到每 150ms 最多一次。连接校验由每次本地 RPC 执行，客户端不再额外发起独立身份检查请求。
- 扫描与执行发出统一进度：开始时间、完成量、总量、单位和当前并发。执行总量来自确认清单；扫描总量为动态发现目录数，显示“动态预估”。不足两个完成样本或两秒观测时不显示数值剩余时间。
- 新版界面检测本地服务协议，旧服务需要安全停止后重启；不能在用户正在执行真实文件操作时强制重启。

## 验证依据与状态
公开字段和接口依据：`https://github.com/Quan666/PikPakAPI/blob/main/pikpakapi/__init__.py` 与 `https://github.com/rclone/rclone/blob/master/backend/pikpak/api/types.go`。官方 CLI 的大小和时间为展示字符串，未用于精确筛选。

用户已反馈真实全盘扫描成功并得到同名冲突清单，证明连接与读取已在用户环境运行。修改后的去重、部分执行及并发扫描通过模拟自动测试；没有由助手执行任何真实文件移动或删除。真实写操作仍待用户审阅并执行验收。

## 1.0.5 默认执行模式（取代上面的逐文件执行策略）
- 用户明确要求取消逐文件核验。默认由 `batch.mjs` 调度，50 个文件一批、2 批并发，按年份批量移动，按删除类别批量移入回收站。旧逐项执行器仅留作兼容和回归测试，不再作为界面默认入口。
- 使用 PikPak 原生 `batchMove` / `batchTrash` 的 `task_id`，轮询 `/drive/v1/tasks/{id}` 确认整批完成。不逐个读取文件详情或回收站状态；目录批次提交前仍判空。
- 依据 https://github.com/rclone/rclone/blob/master/backend/pikpak/helper.go 中的批量请求及任务等待实现，返回没有明确任务状态/编号时保留未知状态。
- IndexedDB 升级到版本 2，保留原操作日志，新增任务元数据、不可变计划、独立批次检查点三个存储。每批状态更新只写薄检查点，避免反复保存整个全盘计划。
- 任务状态包括就绪、运行、暂停、待处理和完成；批次状态包括未提交、提交中、等待远程任务、完成、失败、未知和依赖阻塞。提交前先持久化，防止崩溃后直接重放未知写请求。
- 同一令牌通过 SHA-256 指纹绑定恢复任务，令牌本身不持久化。恢复使用新的活动连接标识；更换令牌必须重新扫描。新扫描替代相同指纹的旧活动任务，避免旧计划意外重新出现。
- 恢复时已完成批次跳过，有任务编号的批次继续等待，从未提交的批次继续提交。未知移动批次仅读取目标目录定位 ID，未知删除批次仅检查这些 ID 的回收站状态；不能确认就不重发。
- 删除重复项仍依赖保留项对应的移动批次完成；混合批次中部分保留项失败时原子拆分阻塞项，其余可提交。正常流程不额外逐文件核验保留项。
- 空目录按深度分层批处理，判空读取最多 4 路并发；未提交批次恢复后必须重新判空。不能以旧判空结果直接删除目录。
- 新版提供恢复任务提示及「继续未完成批次」入口。旧版只存日志，升级首次必须扫描生成新任务，无法凭旧日志恢复完整未知队列。
